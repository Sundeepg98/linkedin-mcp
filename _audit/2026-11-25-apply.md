### 2.1 The shape of the walk

The two-call gate stays. A multi-step apply becomes THREE calls, because a plan
of steps nobody has seen can only be made by walking them, and the shipped
preview never presses anything:

1. **preview** (no token) -- unchanged: the posting is read, the route
   classified, token T1 minted.
2. **dry walk** (T1) -- opens the flow, reads each step, fills ONLY from his
   CONFIRMED bank or LinkedIn's own prefill, presses each step's ONE advance
   control, reads the review step, and NEVER presses Submit
   (`apply_walk.dry_walk_presses`); then runs the inverse (dismiss, Discard,
   verify no draft). It returns the PLAN -- every step, every field, its action
   and bank class, what the review screen will show -- or a NEEDS-OPERATOR list,
   or a refusal naming what it saw; and, with a complete plan, token T2 bound to
   the plan's fingerprint.
3. **confirm** (T2) -- walks again; each step must match the planned step's
   fingerprint (`step_matches_plan`); Submit is pressed once, on the final
   planned step, by `submit_gate`; the outcome is read from the Applied tab
   (the shipped `_read_applied_state`) or the posting's applied state.

Under the ruling `APPLY-FLOW-IS-THE-APPLICATION` the dry walk is the first step of an
application, not a read: it is granted, aimed only at a posting he names
(`OPERATOR-NAMES-THE-TARGET`), and needs him (`OUTWARD-ACTS-NEED-THE-OPERATOR`).

### 2.2 Recognition, by measured structure only

* **The reading contract** (`StepReading`, `FieldReading`, `ControlReading`):
  tags, input types, roles, the `aria-autocomplete` / `autocomplete` /
  `inputmode` tokens, required flags, data-attribute NAMES (never values), and
  the page's words only where they are the question, an option or a prefill.
  `scan_complete` defaults to "not scanned", as `dom.read_apply_modal`'s does. A
  select whose selected option is a placeholder reports no value -- decided by
  the option's empty `value` attribute, never its words.
* **The registry** `apply_walk.SHAPES`: 18 shapes -- five step kinds (contact
  info, resume choice, screening, review, daily-limit-or-pause), eight field
  kinds (text, numeric, select, radio, checkbox, a group of boxes, typeahead,
  file), four controls (submit, advance, dismiss, discard) and the Draft-tab
  verification. **One is MEASURED** (`verify.draft_tab`, evidence the tracked
  skeleton); the other seventeen are PROPOSED, each naming the capture that
  will measure it.
  A test pins the measured set, and a measured shape must cite a tracked
  fixture.
* **Recognition** (`classify_field`, `classify_control`, `classify_step`) reads
  structure; a step's heading never decides its kind. A field outside the
  seven kinds, a step outside the five, a PROPOSED shape, more or fewer than
  one dialog, or an unfinished scan is REFUSED, and the refusal's `saw` names
  the structure in closed vocabularies (an attribute value outside them reads
  `other`, so a page cannot write into a refusal).
* **TODAY THE WALKER REFUSES THE FIRST STEP OF EVERY MULTI-STEP FLOW**
  (`unmeasured_step`, naming the kind it resembles and C-J68-1). That is the
  measured state of the world, the same answer the shipped gate gives with a
  richer description of what was seen.

### 2.3 The answer bank: shared, platform-neutral, and his

**Where it lives, as ruled (orchestrator, 2026-11-25).** One JSON file,
`<jobhunt root>/mcp-servers/_audit/job-pipeline/answer-bank.json`, beside the
job pipeline's tracker. `mcp-servers/_audit` is a NESTED git repository whose
own `.gitignore` ignores `*.json` and `*.jsonl`, so the file is ignored by the
repository that actually contains it -- asked of git from that directory, by
lane pipeline-26's own guard, before the file was created (section 4). The
first choice, beside `jobhunt.json`, was ruled out because pipeline-26
measured `<jobhunt root>/config/` as NOT ignored for new files.

**The path is resolved at runtime, never written into code**
(`apply_answers.locate_bank`, in this order):

1. `JOBHUNT_ANSWER_BANK`, a file path, used as given;
2. `JOBHUNT_HOME`, read as the jobhunt ROOT, as pipeline-26's `jp.state_dir`
   reads it;
3. a walk up from the package, at most 12 parents (pipeline-26's
   `find_root` bound), to the `.jobhunt-root` marker.

No root found is an empty bank that says so, never an error and never a
guessed place. A test holds that the module carries no drive-rooted path.

**The shape: one entry per NORMALIZED QUESTION CLASS, then per-platform field
hints** (the format in full is section 2.3.2). An entry is a class --
`experience.years.nodejs`, `availability.notice_period`,
`work_authorisation.india` -- holding ONE platform-neutral answer. Under
`platforms`, each platform lists the field hints that say which of ITS
questions are this class: their exact wordings, the option set they are drawn
with, and the platform's own name for the field type. Where a platform wants
the answer in its own format -- Naukri's option label for a notice period
LinkedIn asks for in days -- that is a per-platform answer beside the neutral
one, confirmed like it.

* **ONLY `confirmed` IS READ.** `Answer` has no field for the draft; an entry
  whose confirmed block is empty answers nothing. Every answer returned has
  one provenance, `operator_confirmed`, and carries its `confirmed_at`.
* **A question belongs to a class only if its exact wording is listed** in that
  class's hint for that platform, compared after `people_data.sanitise` and
  case folding and nothing more: no keyword, prefix or containment match, and
  no guessing a class from a question. A hint that names `options` matches
  only that option set. An `any` hint serves every platform; a platform's own
  hint beats it, and a hint naming this option set beats one naming none.
* **Families are closed and carry the rules.** Experience, availability,
  compensation and location are VOLATILE: a confirmed entry needs
  `expires_at`, and an expired one answers nothing. Work authorisation,
  self-identification, checks, cover letters and free text about pay are
  NEVER-AUTO: returned with `auto` off, and `auto: "yes"` on one refuses the
  file. A `naukri_import` entry cannot be confirmed until he gives it a real
  family. A confirmed entry that lists no wording on any platform is refused:
  it could answer nothing, and keeping it would look like coverage.
* **The file is refused whole** on anything that is not the bank's schema: an
  unknown key anywhere (a misspelt `confimed` would otherwise be an answer he
  gave, silently dropped), a field that is not text, an unknown family, kind
  or platform, a bad numeric, checkbox or date, an option answer outside its
  hint's options, a confirmation dated in the future or an expiry before it, a
  duplicate id, or one wording answered by two classes -- and **no refusal
  carries a value** (checked with a planted value in sixteen shapes and four
  documents; a JSON error is reported by line and column only).
* Read fresh on every call; no module-level cache.

### 2.3.2 The bank's format, for pipeline-26 (schema `jobhunt-answer-bank/1`)

A JSON object: `schema` (exactly `jobhunt-answer-bank/1`), `about` (free text
for him, never read), and `entries`, a list. Every entry has exactly these
keys; any other key refuses the file:

    {
      "id": "availability.notice_period",     the class: 1-96 of a-z 0-9 _ . -, unique
      "family": "availability",               closed: decides expiry and never-auto
      "input_kind": "text",                   text numeric select radio checkbox
                                              multi_select typeahead
      "platforms": {                          any linkedin naukri uplers instahyre
        "naukri": {
          "questions": ["<exact wording as Naukri draws it>"],
          "options": ["<label>", "<label>"],  empty = any option set
          "native_type": "Radio Button"       the platform's own name; never matched
        }
      },
      "draft": {"value": "", "per_platform": {}, "source": ""},     NEVER read
      "confirmed": {
        "value": "",                          the neutral answer
        "per_platform": {"naukri": ""},       a platform's own format of it
        "confirmed_at": "YYYY-MM-DD",         required once anything is confirmed
        "expires_at": "YYYY-MM-DD",           required for a volatile family
        "auto": ""                            "" (the family decides), "yes", "never"
      },
      "notes": ""
    }

Formats: numeric is digits with at most two decimals; checkbox is `checked` or
`unchecked`; select and radio are one label exactly as drawn; multi_select is
labels joined by ` | `. The answer for platform P is `confirmed.per_platform.P`,
else `confirmed.value`; it is checked against every hint's input kind and
options at load, so a bank that loads cannot hand a platform an answer its
hint forbids. The read API is `apply_answers.lookup` (section 2.3.1, row 1);
the location order is section 2.3; the Naukri join is `naukri_cache_key`,
`import_naukri_cache` and `naukri_cache_report`.

### 2.4 The plan, and NEEDS-OPERATOR

Per field (`_field_plan`): a LinkedIn prefill with no confirmed class is kept and
labelled `source: linkedin_prefill`; a prefill that differs from his confirmed
answer STOPS the walk (`prefill_differs_from_confirmed`, the value not
printed); an empty field fills from his confirmed class (`fill`, `choose`,
`check`); a confirmed select or radio answer must be one of the drawn options
exactly; an empty field with no confirmed class is NEEDS-OPERATOR unless the page
marks it optional (an unstated flag counts as required). **A checkbox is never
kept on LinkedIn's tick alone** -- a box can be a consent or a follow of the
employer's Page -- so a ticked box with no confirmed answer stops the walk. A
group of boxes (`multi_select`) is answered by labels, each one drawn, and
compared as a set. A file input is never filled (uploading is census J 70).
The walker asks the bank for LinkedIn's rows and `any` rows only. **A
never-auto answer, and every value kept from LinkedIn's prefill, is listed in
the plan's `answers_he_must_see`** -- what the preview puts in front of him
before he hands back the confirm token.

NEEDS-OPERATOR stops the walk at that step and quotes EVERY unanswered question
on it, each with its input kind and, for a select or radio, the options drawn
-- sanitised, capped and marked `untrusted_third_party_text`. Nothing is
inferred from the page, his profile or his resume; a lone option is not chosen
for him.

Per step (`plan_step`): before the last, zero submit-hook controls and exactly
one advance control; the last must be a measured review step with one submit
and no advance. Per walk (`plan_walk`): at most 12 steps; a press that did not
move the flow (two equal step fingerprints) stops it (`stuck`). The plan's
fingerprint covers every step's structure and every planned value's class
and digest, so a bank edit after the preview invalidates the confirm.

### 2.5 The confirm walk, and the one press that cannot be taken back

`submit_gate`: a complete plan (code 0), then nine conditions (codes 1-9),
each under its own code and ordered so that every one is reachable alone:
**no submit pressed yet on this walk**; **the final planned step**; a finished
scan; the step matches the plan; exactly one submit-hook control; visible and
enabled; its name corroborates the hook; no advance control; a MEASURED review
step.
`confirm_presses` is open, one advance per earlier step, and Submit once.

### 2.10 Batch Easy Apply (L5): designed here, not built

A thin layer over this walker, on the rails of `instahyre_apply_bulk`, whose
own words state the principle: a confirm-gated bulk apply "is the same N
applications, to the same employers, equally permanent. What it removes is
N-1 CONFIRMATIONS, and every rail here exists to hand back exactly what that
collapse takes away." Its future shape, a proposed name and no tool yet:
`linkedin_apply_jobs(job_ids, expected_count, confirm_token="")` (proposed). Every
rail below is a refusal, never a repair:

1. **THE IDS ARE HIS.** An explicit list of numeric job ids, each a posting he
   named (`OPERATOR-NAMES-THE-TARGET`). The tool never assembles one: no
   "apply to all", no filter, no "top N by score". An empty list is refused,
   not read as everything; a duplicate id is refused, not deduplicated.
2. **A HARD CAP OF 5, AND OVER IT IS A REFUSAL, NEVER A TRUNCATION.** Applying to
   the first five of nine and reporting success is the failure this must not
   have. Five, because each job costs about six page loads (a dry walk -- the
   posting, the flow, the Draft tab -- and a confirm walk -- the posting, the
   flow, the Applied tab), and five jobs is 30 of the session's 40
   (`LIVE-BUDGET-40-LOADS`). The cap is a constant with that arithmetic beside
   it; raising it means re-doing the arithmetic.
3. **`expected_count` RESTORES THE ARITHMETIC.** Stated by the caller apart
   from the list; it must equal the number of ids that resolve to a complete
   plan, or nothing is minted and nothing is sent.
4. **THE PREVIEW NAMES EVERY JOB, ONE LINE EACH**: id, title, employer, the
   route (`linkedin_apply`, or the refusal that stops it), steps walked, and
   the count of answers he must see. Below the lines, each job's own
   `answers_he_must_see`. He confirms against the lines, never against a
   count. The preview IS one dry walk per job (section 2.1), run serially and
   paced, each with its own inverse and Draft-tab check.
5. **ALL OR NOTHING AT THE PLAN.** The batch token is minted only when EVERY
   listed job produced a complete PLAN and the count matches. A job that needs
   him, refuses, or routes off-site is named, and nothing is minted; he
   answers or drops it and previews again.
6. **ONE TOKEN, BOUND TO EVERYTHING.** Single-use, short-lived, bound to the
   ordered id list, `expected_count`, and every job's plan fingerprint (so a
   bank edit after the preview voids it, as for one job).
7. **THE CONFIRM RE-WALKS EACH JOB AND SUBMITS EACH ONCE.** Serially, paced;
   each step must match its plan (`step_matches_plan`), each Submit passes
   `submit_gate` with that job's own count of presses, and each outcome is
   read from the Applied tab -- state is the evidence, as
   `instahyre_apply_bulk` reads its queue after the write.
8. **THE FIRST STOP STOPS THE BATCH.** Any refusal, drift, sign-in challenge or
   unexpected page on job k runs job k's inverse and ends the batch; a
   daily-limit or rate-pause state ends it with `retry: never`. Jobs after k
   are not touched. The result lists, per id, `applied` (verified),
   `not_applied` (verified), `unknown`, or `not_reached` -- never a count alone.

Nothing of this is built: it needs the walker wired first, and the walker
needs C-J68-1.
