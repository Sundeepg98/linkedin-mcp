## 1. `THIRD-PARTY-PROFILE-FORBIDDEN` -- FILED, `M M5`

This blocker had never been worked. The last wave to touch the absent four
(`_audit/2026-09-19-the-empty-blockers.md`, section 4) listed it under
"Untouched this wave."

### 1.1 The cell names a CONDITION, not a row

`_audit/2026-09-03-linkedin-gap-blockers.md:326`:

> `PERMANENTLY_FORBIDDEN[load_a_third_partys_profile_to_measure_a_control]`
> reaches it; the row records the collision itself

So the search is not for a resembling capability. It is for a row whose OWN TEXT
records that collision -- a closed question, answerable by sweep.

### 1.2 The sweep: the candidate set is TWO, and it is measured

Over all 409 frozen GAP rows at `1c08e5f`:

    "collid|collision"                                          2 hits
    "forbidden|permanently|ruled out|refus|R4|emission"         12 hits

The two are `P C8` and `M M5`. Of the wider twelve, the other ten each name a
DIFFERENT rule -- `/endorse` at `P E6`, `/edit/` at `M M11`, `/withdraw` at
`M C62`, `/invite` at `M C69` -- and every one of those is a separate ledger
blocker that already closes COMPLETE. `P C8` is also the only row in the whole
409 that names `PERMANENTLY_FORBIDDEN` at all.

### 1.3 `P C8` is excluded twice over, neither time by a ranking

**(1) Its collision is CONDITIONAL and out of scope.** Its text reads: the
feature "works on **another member's profile too** -- which **would** collide
with `PERMANENTLY_FORBIDDEN[...]`". Saving his own profile as a PDF requires no
third-party load. The entry does not REACH it, which is the ledger's own verb.

**(2) The ledger's other cell refutes it.** The same author ranks that
capability at index 58 `PROFILE-PDF-DOWNLOAD` -- 1R, cost 2, reversible YES,
queue DECIDE. One author cannot, in one document, rank a capability as a cost-2
buildable DECIDE and also place it under a `PERMANENTLY_FORBIDDEN` entry at cost
0 RE-FILE.

### 1.4 `M M5` satisfies both halves of the cell

Frozen text, `1c08e5f:_audit/_census/messaging-and-content.md:336`:

> `| M5 | Send an Open Profile message | ... | needs a third party's profile
> loaded to find the control -- collides with the who_viewed_me emission ruling |`

* **"reaches it"** -- the forbidden act is REQUIRED, not optional. The control
  cannot be found without it.
* **"the row records the collision itself"** -- it does, in those words.
* **The ruling it names IS that forbidden entry**, by the entry's own shipped
  reason rather than by resemblance.
  `writes.PERMANENTLY_FORBIDDEN["load_a_third_partys_profile_to_measure_a_control"]`
  reads: *"A profile view is an EMISSION, and this server can read the receiving
  end of that signal: `linkedin_who_viewed_me` returns rows, reaching 365 days
  back."* `P C8` names the entry by its KEY; `M M5` names it by its
  JUSTIFICATION.

**The queue corroborates.** The ledger queues this blocker RE-FILE, "nothing to
do but correct the census". `M M5` is exactly a mis-filed state -- amendment C1
of `_audit/2026-09-19-profile-modals-measured.md` caught it GAP while its twin
`N158` was already EXCLUDED-RULED in `network.md` -- and the census has since
re-filed it. `P C8` is still GAP today.

### 1.5 The rival blocker was tested too

`M M5` was also tested against `MESSAGE-ADDRESSING` and rejected on the source's
own words: blocker 57's stated condition is *"the chip rail has never been
observed"* (`_audit/2026-09-05-messaging-rows.md:215`), which is a compose-surface
observation problem. `M M5`'s stated blocker is the profile load. Different
conditions.

### 1.6 Filed as RECON-DOC, and why not the stronger class

The census DID act on `M M5` -- but under **R9** (InMail and outreach
automation), a different ruling from the one this blocker is named for. Claiming
`RECON-CENSUS-COMMITTED` off a partial match would manufacture auditability.

**REOPENER, and it is coupled:** any source naming `P C8` for this blocker
retracts this line AND re-opens `P C8`'s `PROFILE-PDF-DOWNLOAD` filing. The two
cannot move independently. I did not write that filing and do not vouch for it;
exclusion ground (1) above does not depend on it.

### 1.7 Why a name-token matcher could not have found this

`P C8` carries the only verbatim occurrence of that forbidden key in the frozen
GAP set, and it sits in the row's **REASON cell**. The `ca374c6` matcher scored
CAPABILITY TEXT against blocker NAMES, so the one string that decides this
blocker was outside everything it read. The `empty-blockers` wave reached the
same lesson from the other side -- *"do not point COUNTING at an under-supplied
blocker; do point the REASON CELL at it."*

MEMBERSHIP: *"J92-J98 and P I13-I16 were GAP there (11 rows, all W, matching the

### 3.3 Verdict

The boundary currencies and the closed 120-sum both point the same way: `P I16`
stays with blocker 20, and **blocker 81's published "1 row" has no referent

**NOT FILED, deliberately.** Filing `P I16` here would close one blocker by
