# Lane search-fix26: an empty job search is never silent, and the AI search is a refusing fallback

Lane `search-fix26`, 2026-11-26. Base: master `4c62196`. Branch `worktree-agent-search-fix26`.
OFFLINE: no LinkedIn load, no port 9224, no Chrome start or stop. Every page this lane read was a
capture already on disk, or a fixture loaded into a local headless Chromium by the test suite.

**What this lane builds on.** Lane search26's research record (outside the repo,
`linkedin-search-migration/2026-11-26-new-job-search.md`): LinkedIn draws "We're gradually retiring
classic job search starting in September" over `/jobs/search/`; its AI search at
`/jobs/search-results/` is server-driven UI with no `/jobs/view/` link; the shipped harvest keys 0
cards there; `linkedin_search_jobs` ran it with `allow_empty=True` and never checked where it landed.

**Rulings built to** (orchestrator, 2026-11-26):

- `Q-SEARCH-ROUTE-POLICY`: classic stays the PRIMARY route while it serves. The AI route is the
  FALLBACK, and it REFUSES every filter not yet measured on it.
- `Q-FILTER-FIRES-SEARCH-CAP`: a filter-driven re-query counts as a search against the
  5-per-session cap (`D1-SEARCH-AS-READS`).

**Evidence classes:** VERIFIED (measured by a named instrument), DERIVED (follows from verified facts
or from reading code), ESTIMATED, UNVERIFIED.

## 4. The fallback (piece 4), per `Q-SEARCH-ROUTE-POLICY`

Used ONLY when the landing is `ai_search`. It reads the page the classic request LANDED on: **zero
re-queries, zero presses**, so a call is still one load, one search per place
(`Q-FILTER-FIRES-SEARCH-CAP`; `test_the_ai_fallback_returns_the_keyword_search_in_one_load` asserts
`navigations == [the asked-for classic address]` and `pages_loaded == 1`).

In order, on the AI landing:

1. **A refused argument refuses the call**, naming every refused argument and its ground, before a
   row is shaped. The refusal also reports the page's Easy Apply toggle as drawn, not drawn, or
   unread. It never quotes an argument's value.
2. **The landing must carry the keywords asked for** (`landed_query_matches`: one `keywords` key,
   equal after case and whitespace folding). An AI page for any other query is not this search.
3. **A zero refuses** (the AI empty state is uncaptured, G7).
4. Otherwise the rows, with `route: "ai_search"`, `results_label`, `pager`, `easy_apply_filter`, and
   a note saying it is the fallback.

| honoured on the AI route (`AI_ROUTE_HONOURED`) | ground |
|---|---|
| `keywords` | session 11's capture is `/jobs/search-results/?keywords=<generic role words>`, relation SERVED exactly, 25 cards (VERIFIED, search26 section 2.1) |
| (`limit`) | never sent to LinkedIn; it trims the rows this process returns |

| REFUSED on the AI route (`AI_ROUTE_UNMEASURED`), by name, when set off its default | ground |
|---|---|
| `location`, `locations` | LinkedIn's 105 AI-route links address a place by `geoId` + `distance`, never a text `location` (search26 2.5) |
| `remote`, `experience_level`, `job_type` | drawn as pills on the AI page; their address spelling is unmeasured (search26 3.2) |
| `date_posted` | LinkedIn's own AI links spell it `f_TPR`; no capture shows a composed `f_TPR` honoured |
| `company_id` | no capture shows an employer-scoped AI search (G5) |
| `easy_apply` | the toggle is DRAWN (presence measured: `Filter by Easy Apply`, twice, unchecked); its spelling and effect are unmeasured (`f_AL` on 0 of 105 AI links; C-SRCH-3a) |
| `under_ten_applicants`, `fair_chance_employer` | no capture shows them on the AI route |
| `in_your_network` | drawn as a toggle (`In my network`); spelling unmeasured |
| `sort_by` (`date`) | no capture shows a sort order on the AI route |
| `start` (> 0) | the AI pager is buttons with no address (G4) |

`test_the_ai_route_table_covers_every_parameter_the_tool_takes` holds the two tables to the tool's
signature: a parameter added to `linkedin_search_jobs` without an AI-route classification fails it.

**Easy Apply, read narrowly.** The brief says the fallback honours "whatever filter is measured on
the AI route; at present that's the Easy Apply toggle's presence only". Presence is what is
measured; the effect is not, and the registered ruling refuses every filter not yet measured. So
`easy_apply=True` REFUSES on the fallback, and the refusal reports the toggle's presence read off the
landed page. A caller wanting Easy Apply postings on the AI route can call without it: every AI row
carries its card's own `easy_apply` mark (8 of 25 on the capture). Question Q1 asks whether to
honour it instead as a post-filter on that mark.

## 5. The AI-page fixture and its builder (piece 2)

`tests/fixtures/live11/jobs_search_ai.html` (40199 bytes, ASCII), built by
`scripts/_build_ai_job_search_skeleton.py --raw <the preserved raw capture>` from the main
checkout's gitignored `_state/preserved/live11-2026-11-25/jobs_search_keywords.html` (session 11,
2026-11-26 00:30 IST, SERVED, 25 cards). Builder output (counts and a digest only):

```
cards 25 | titles 25 | twins 5 | companies 25 | places 25 | topics 5 | synthetic ids 25
texts kept 112 | texts replaced 36 | output texts checked 239 | output attributes checked 907
input texts searched for 73 | bytes 40199
```

The file's sha256 begins `b126b8e16cead5b9` (`sha256sum`, run on the file, not printed by the
builder). The builder printed that digest itself in its first version, and
`tests/test_page_text_is_never_printed.py` counted it: a digest of page-derived text reaching a
print, plus the counts printed off the returned tuple (`scripts/_build_ai_job_search_skeleton.py
0 -> 2`). It now prints only the builder's own tallies and the written file's byte length; the
rebuilt fixture is byte-identical.

**It is a WHITELIST, not a scrub.** It keeps every element and its nesting (dropping undrawn ones
and `svg` contents), attribute values only from LinkedIn's code vocabulary validated by shape
(`role`, `type`, `tabindex`, `aria-*` states, `checked`, `data-display-contents`, `data-testid`,
`data-sdui-screen`), and TEXT only when it is a LinkedIn UI word (equality, a closed list) or a closed
grammar (a time-ago, a posted line, a results total, an alumni count). Everything else is rewritten:

- posting ids become `4000000101` to `4000000125`, the real ten-digit shape, the same id for a
  card's inner copy and for the page's `currentJobId` links;
- titles, companies and places become `Role Title NN`, `Company NN`, `Place NN` (the place keeps its
  `(Remote)`/`(Hybrid)`/`(On-site)` word), each written INTO THE FIELD'S OWN SLOT, so a reader bound
  to the wrong element returns the wrong neutral value;
- the title's plain-span twin becomes `Accessible Copy NN`, a NEEDLE no row may return;
- the 5 query-topic chips become `Topic 1` to `Topic 5`, label and text alike; the alert toggle's key
  loses the query words and digit runs it carried; every other component key is `k<n>`, every
  `id`/`for` is `id<n>` (pairs kept), every `href` is a bare LinkedIn path from a closed list, the
  synthetic search link, or `#`; `alt` is empty; any other `aria-label` is `x`; any other text is `x`.

**It checks itself before writing**, both ways: `verify()` parses the output and refuses unless EVERY
text and attribute value is one of the declared forms (a positive check: an unlisted value cannot
pass); then each input text of six characters or more outside the vocabulary is searched for in the
output's texts. **Shown failing** by `test_the_alphabet_check_refuses_a_planted_value`, five plants
(a name in a field, a name in a Dismiss label, a member-profile href, a non-synthetic posting id, an
unknown attribute), each refused. The committed fixture passes it
(`test_the_committed_fixture_passes_the_builders_alphabet`). The raw is never written anywhere and
nothing prints a value it read.

**Why `live11/` and not the top of `tests/fixtures/`.** It landed at the top first, where the
fixture-privacy guards glob. `tests/test_surface_census.py` sweeps that same directory with the
census's control reader and PINS what it reads, file by file and in total; the new page moved seven
of those pins (`the sweep read 679 controls, not 553`, among them). Those pins describe the existing
corpus, and a live-session skeleton belongs with its siblings in a per-session directory
(`live1/` to `live9/`, where jmn26's `live2/j107_search_alert.html` also sits), which no corpus sweep
reads. So it moved, and the privacy patterns those top-level guards apply are applied to it by name
in `test_the_fixture_passes_the_repositorys_fixture_privacy_patterns`, IMPORTED from
`test_sdui_surfaces_fixture.py` rather than rewritten. The identity sweep
(`test_no_committed_identity.py`) reads every committable file wherever it sits.
