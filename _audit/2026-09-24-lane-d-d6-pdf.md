## 3. `P C8` -- THE TRANSPORT IS BUILT, AND THE ROW STAYS GAP ON THE PRESS

### 3.1 What was built

`linkedin_server/cdp_download.py`, the transport `D4-NO-OWN-BROWSER-CONTEXT`
names:

1. a DevTools session on the BROWSER TARGET, from
   `Browser.new_browser_cdp_session()` -- in the installed driver that is one
   `Target.attachToBrowserTarget`: it attaches to what is there, and makes no
   context and no tab;
2. `Browser.setDownloadBehavior` with `allowAndName`, a fresh run directory
   under `_state/downloads/` and download events on for that session;
3. the caller's `trigger` -- the act that starts the download; the module does
   not know what it is;
4. `Browser.downloadWillBegin` names the GUID, `Browser.downloadProgress`
   says `completed`; the file lands under the GUID, a name the BROWSER chose;
5. renamed to `<label><suffix>`, a name THIS SERVER chose, and checked against
   the kind the caller expects (`b"%PDF-"` for a PDF);
6. `finally`: the behaviour set back to `default`, the session detached.

**Off unless `LINKEDIN_ENABLE_CDP_DOWNLOADS` is set**, read at call time; off,
it returns `downloads_disabled` before making a directory or a session. In
LAUNCH mode it returns `not_attached`. `CDP_METHODS` is a closed table of one
method, and `_send` -- the only DevTools `send` in the package -- refuses
anything else. The page's suggested file name and the download's url never
leave the module; `from_linkedin` is one boolean about the url's host. A
failure carries an exception's TYPE and never its text. The path returned goes
through `config.display`. Every outcome is one of 16 words in `WHY`.

**The window, stated because it is the cost.** The behaviour belongs to the
browser CONTEXT, and his own tabs share it. Between the set and the restore --
bounded by the two timeouts, 20 s to begin and 60 s to complete -- a download
HE starts would land in the run directory too. The first to begin is the
capture's; any other is counted in `other_downloads` and left where it landed.
Nothing in the module deletes a file.

**"Restored" is sent and acknowledged, not measured.** The protocol has no
call that reads the behaviour back. `behaviour_restored` says the `default`
call returned without raising.

### 3.3 What Playwright already does at attach, and why the transport does not lean on it

DERIVED from the installed driver source (`playwright` 1.63.0 in this
repository's virtualenv on 2026-09-24), NOT OBSERVED LIVE:

* `_connectOverCDPImpl` builds the adopted default context's options as
  `{noDefaultViewport: true}` unless `noDefaults` is passed, and makes a
  temporary artifacts directory it removes when the connection closes;
* `validateBrowserContextOptions` then sets that context's download option to
  `"accept"`;
* `CRBrowserContext.initialize` sends `Browser.setDownloadBehavior` with
  `allowAndName`, NO context id -- so the default context, his own tabs -- and
  that temporary directory.

`cdp_bridge.attach()` passes neither `no_defaults` nor `artifacts_dir`. So
the transport test's structural sentence was exact about this package and not
about the library under it: **while this server is attached, a download in any
of his tabs is written, under a GUID, into a temporary directory that is
removed when the server disconnects.** That is a hazard to his own files,
recorded in section 5.2 for `cdp_bridge.py`'s owner.

The transport sets the behaviour itself for three reasons: that default is a
library's and a version can move it; it puts the file where this server does
not name it; and it is never undone. After a capture, his browser is on
Chrome's own `default` -- his state before anything attached -- not on
Playwright's.
