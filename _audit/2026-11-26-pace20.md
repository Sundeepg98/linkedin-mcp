# Lane pace20: the server's default spacing between page loads is the ruled 20 s

Lane pace20, 2026-11-26. Base: master `7760a5f` (master CI run 45761862526,
green). Branch `pace20`. One change: `LINKEDIN_MIN_INTERVAL_S` defaults to
20.0, not 3.0.

**OFFLINE THROUGHOUT.** No LinkedIn page was loaded, no browser was started or
attached to, and port 9224 was never touched. `_state/LIVE_SESSION_ON` was
absent at every check.

---

## 1. Why

`LIVE-BUDGET-40-LOADS` (`_audit/RULINGS.md`) rules LinkedIn page loads at
least 20 seconds apart. The server's own spacing,
`config.MIN_NAVIGATION_INTERVAL_S`, read `LINKEDIN_MIN_INTERVAL_S` with a
default of `"3.0"`. The live lane has always set the variable to 20, so the
ruling held where that lane ran and nowhere else.

The apply pipeline's red team measured the gap (its record of 2026-11-26,
section "Re-check (cda616d)", attack N-01d; the record is kept outside this
repository). The pipeline's hook spaces call STARTS. Inside one call, every
navigation waited only the 3.0 s default: a 5-place `linkedin_search_jobs`,
the three loads of `linkedin_group_memberships`, a two-load preview. Its fix
was this interval at 20 s, "the one place that sees each load".

## 2. The change, and what it costs

* `linkedin_server/config.py`: the default `"3.0"` becomes `"20.0"`. The
  environment override is unchanged.
* THE COST IS DELIBERATE. A call that makes N loads now takes at least
  20 x (N - 1) seconds: 40 s for three loads, 80 s for a 5-place search.
  MEASURED: the server has no per-call timeout that could cut such a call
  short. Nothing wraps a whole tool call in a timeout. The package's
  `asyncio.wait_for` sites each bound one operation: the CDP probe's read of
  `/json/version` (`cdp_bridge.py`), a download's begin and finish after its
  press, and a CDP session's open and detach (`cdp_download.py`, which calls
  no `goto`). None spans a navigation, so none spans a rate wait.
  `NAV_TIMEOUT_MS` (45 s) bounds one `page.goto` and starts after the rate
  wait. The per-process call lock (`_call_lock`, taken with `async with`) has
  no timeout either: a second call queues behind the first for as long as
  its loads take. Whether an MCP client allows a call that long is the
  client's setting, not this repository's.

## 5. The suite at 20 s: a fake rate clock

MEASURED: two real-clock navigations on a fresh `LinkedInBrowser` at the new
default took 20.01 s. Every test that made a second load would pay that.
`BROWSER` is also a module singleton, so a stamp one test leaves would make
the NEXT test's first load wait, which is an order-dependent cost under
`--dist loadfile`.

* `browser.py` holds the slot's clock and sleeper as module attributes
  (`_rate_clock = time.monotonic`, `_rate_sleep = asyncio.sleep`). Both the
  wait and the stamp read them. Production binds the real ones.
* `tests/conftest.py`: `rate_clock` (autouse) runs every test on a
  `FakeRateClock`, from a cold slot. The clock starts at 1e6, because a stamp
  of 0.0 reads as "never navigated" and would skip the next wait. A test that
  slept on the clock carries the junit property `rate_slot_fake_sleep_s`.
  `real_rate_clock` opts a test out.
* `tests/test_browser.py`: the spacing test and its zero-floor control keep
  the REAL sleeper at a quarter second; they are the proof that production
  really sleeps. "The first navigation is not delayed" and "a failed
  navigation still consumes its rate slot" moved to the fake clock and now
  assert exact values at 20 s.

WHICH TESTS RELIED ON FAST NAVIGATION was measured on the full suite rather
than inferred: lane CI run 45784201192 (14747 tests), and its per-test times
against the base run 45761862526 on the same ubuntu 3.13 cell.

* SIX TESTS carry `rate_slot_fake_sleep_s`, 300 fake seconds in all. Two are
  this lane's: the burst in `test_navigation_pace` (40 s) and the failed
  navigation in `test_browser` (20 s). FOUR are in
  `test_readers_emit_no_page_string`, at 60 s each, which is three waits of
  20 s: `test_the_driven_set_has_not_silently_shrunk`,
  `test_every_vacuous_reader_is_driven_or_names_what_would_drive_it`,
  `test_a_reader_stubbed_to_return_early_is_not_counted_clean`, and
  `test_no_reader_logs_what_a_failing_library_said[analytics_hub:read_analytics_hub]`.
  On the real clock at 20 s those four alone would add 240 s to every run.
  At base they spent up to 9 s each; the last fell from 10.13 s to 0.94 s.
* CARRYOVER is the cost the cold slot removes. Six tests fell from 2.96-3.00 s
  to 0.00-0.02 s and carry no property, so the wait they lost was for a stamp
  the PREVIOUS test had left. Four are in `test_auth`; two are cases of
  `test_no_reader_carries_a_page_string_out` (`server:_goto_self_profile_asserted`
  and `server:_own_item_veto`). The reverse band (near zero at base, 0.5 to
  3.2 s now) holds one test, which is the noise floor. At 20 s each of those
  waits could have been 20 s, and a 20 s window catches far more neighbours
  than a 3 s one did.
* NOTHING SLEPT 20 s FOR REAL. No test is slower than at base by more than
  4.85 s; one real wait would show as about +17 s. Six are slower by 2.5 s or
  more (four of them repository sweeps or census pins), and none of the six
  carries the property, so none of them waited in the rate slot.

## 6. The live runner reads this interval too, and nothing changes for it

Session 11's runner is `runner_s11.py`. The copy that the session record
places in `_state/live11/tools/` is no longer on disk, so its scratch copy was
read. It launches with `LINKEDIN_MIN_INTERVAL_S=20`, and it reads the
interval in two places:

* `_environment_refusal()` (the harness, both sessions) refuses to run when
  `config.MIN_NAVIGATION_INTERVAL_S` is below 20.
* `_install_counter()` wraps `BROWSER.goto`. The harness's own ledger waits
  out 20 s since the last ledgered load (`gap_remaining`, `MIN_GAP_S` = 20,
  persisted in the ledger, so the wait holds across processes). Then it calls
  the original `goto`, whose rate slot spends this interval in-process.

The runner's other sleeps (0.5 to 3 s) are settles inside a page after a
press, not gaps between loads.

So the live rule was already 20 s, and it stays 20 s. One gate moves, in the
safe direction: a session that FORGOT the variable used to be refused (the
default read 3.0). It is now admitted, at 20 s. The refusal still fires for
any override below 20.
