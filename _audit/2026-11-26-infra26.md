### 1.1 The census: `scripts/caller_census.py`

The census reads every tracked `.py` file's syntax tree, plus every `.py` under
each `--extra` root, and BINDS a reference before it counts it:

* **DIRECT**: a bare-name load in the defining module, as a call or as a value,
  or a load of a name imported from it.
* **ATTRIBUTE**: `<alias>._read_cards`, where the alias is bound to
  `linkedin_server.server` by any import spelling, including the dotted chain.
* **GETATTR**: `getattr`, `hasattr`, `setattr` or `delattr` with the literal name.
* **IMPORT**: an import of the name, relative spellings resolved.
* **UNRESOLVED**: a receiver the census cannot bind. It is COUNTED as a
  possible caller, never dropped. A file that fails to parse is counted too.

Two kinds of hit are listed but NOT counted: OTHER, a same-named function in
another module, and STRING, any string constant that mentions the name.

Run on `3c656df`, the census read 717 tracked files plus the 12 `.py` files
of the gitignored live-runner directory. Its counts: DEF 1, DIRECT 0,
ATTRIBUTE 0, GETATTR 0, IMPORT 0, UNRESOLVED 0, PARSE-FAILED 0, OTHER 0, and

## 2. `NAVIGATION-CEILING-MADE-TRUE`: three per tool call, enforced

### 2.1 Disk disagreed with the ruling's premise, and was reported first

The ruling says tools "reach 3", and "Raise it to the measured maximum, 3".
Measured with the pipeline repository's `tests/nav_census.py` on `3c656df`.
That census is static, follows real calls only, and its loop bounds are its
hook test's own. This repository has no navigation census of its own. Over 91
tools:

| most loads one call can make | tools |
|---|---|
| 5 | `linkedin_search_jobs`: the `locations` fan-out, one load per place, `jobfilter.MAX_LOCATIONS` = 5 |
| census-unbounded | `linkedin_login`, `linkedin_login_browser`: a `while` loop whose `check_auth(page, warm=False)` loads nothing at runtime; real maximum 2 |
| 3 | 31: every write (`_write_tool`'s preview read, then the act), `linkedin_group_memberships`, `linkedin_surface_census`, both profile editors |
| 2 | 12 |
| 1 | 41 |
| 0 | 4 |

So a counter refusing every fourth load would break every 4- and 5-place
search. The lane reported this to the lead before building anything. It
offered three options: (A) 3 per call, with the fan-out cut to 3 places;
(B) a ceiling of 5; (C) 3 per call, with the search declaring its own
fan-out, capped. It recommended (C).

Two more couplings were measured on the way:

* `config.MAX_NAVIGATIONS_PER_CALL` was ALSO the people readers' loop bound:
  `linkedin_who_viewed_me` reads `urls[:MAX_NAVIGATIONS_PER_CALL]`.
  `tests/test_a_people_reader_reads_one_page.py` holds that bound at 2 or
  less, one page and its fallback. Raising the ceiling would have widened the
  people loop. It is split out: `config.PAGE_AND_ITS_FALLBACK = 2`.
* **THE SCOPE IS THE TOOL CALL, NOT THE BROWSER SESSION.** First, the census
  was re-run counting `session()` entries instead of `goto`. 86 tools enter
  `BROWSER.session()` once per call, and only the search enters it once per
  place. That looked like a per-session counter would do. It would not. The
  live runner and the tracked probes load MANY pages inside one session: in
  `runner_s11.py` (read only), `phase_company` loads five company tabs and
  `phase_own_pages` loops `load()` inside one `async with BROWSER.session()`.
  A per-session ceiling would refuse the runner's fourth load. The lead was
  told of this correction before the build.

### 2.2 What was built

* `linkedin_server/call_ceiling.py` (new) holds a per-call budget in a context
  variable. `PerCallCeiling`, a fastmcp middleware (`on_call_tool`), arms that
  budget for every `tools/call`. `spend(url)` counts one load, or refuses it
  with `NavigationCeilingError` (`kind` `navigation_ceiling`). The refusal
  names the loads made, the ceiling, and the refused page's FAMILY (its first
  path segment, never the address). `allow_fan_out(n)` raises this call's
  budget, capped at `jobfilter.MAX_LOCATIONS`; outside a tool call it does
  nothing, and it never lowers a budget.
* `linkedin_server/browser.py`: `goto` calls `call_ceiling.spend(url)` after
  its doors (a refused address costs nothing) and BEFORE the rate slot and the
  page, so a load over the ceiling is refused without being made. Outside a
  tool call nothing is counted. That is the runner's, the probes' and the
  direct-call tests' path, and their own ledgers bound them.
* `linkedin_server/server.py`: three self-contained hunks.
  `mcp.add_middleware(call_ceiling.PerCallCeiling())` follows the `FastMCP(...)`

  `linkedin_search_jobs` calls `call_ceiling.allow_fan_out(len(places))` where

* `linkedin_server/config.py`: `MAX_NAVIGATIONS_PER_CALL = 3`, whose comment

* `linkedin_server/errors.py`: `NavigationCeilingError`.
* `README.md`: the risk table's "One page load per tool call ... no fan-out"
  row and the rate-discipline bullet "One page load per tool call" are both
  corrected. They now name the ceiling, the measured maximum, the tools that

  to say.
* `linkedin_search_jobs`'s docstring opened with "One page load per call",

## 4. PEOPLE-GATE v2: `scripts/people_gate.py`

### 4.1 What it is

`judge(html, *, slug, page_url, page_key, own_cache=...)` judges the STRING a
capture is about to write. It returns a `Verdict`: `keep-raw` or
`withhold-raw`, reasons as closed sentences that carry counts, per-rule
counts, and the string's digest (`covers(text)`). No value from the page is
ever in a reason, a count key or a repr. The orchestrator's six rules, in its
order:

* **R1:** member urns of the four member types (plain or percent-encoded),
  and bare encoded member ids, that are not his, anywhere in the string.
* **R2:** profile-display assets that are not his, in a DOM image, anywhere in
  the string, or in a payload `vectorImage`.
* **R3:** a `PhotoFilterPicture.a11yText` that holds a name other than his.
* **R4:** link-less social-proof lines that name someone, in visible and
  hidden text, labels and payload strings. The templates are "<name> and N
  others", "<name> & N other connections work here", "<name> works here" and
  "<name> is hiring". The templates and the classifier that tells a person
  from interface text and organisations are ported from rawsweep26's
  `sweep.py`.
* **R5:** an events page is skeleton-only by CLASS: an `events` path segment,
  a capture key naming events, or an event entity in the payload.
* **R6:** the verdict is about the exact string judged, and carries its
  digest.

Two more rules are kept. **L1** is v1's own rule, member links that are not
his, now read off the string. **N1** counts name slots
(`PEOPLE-GATE-COUNTS-NAME-SLOTS`): the fixture guard's own slot reader,
IMPORTED, never copied, plus the profile-card name element the unfollowed
list drew. His own profile links are read as the self alias, so the text of
a link to HIM ("View profile") is not a name.

**FAIL CLOSED.** An id it cannot tie to him counts as not his. A slot reader
that fails to import withholds. A page that cannot be parsed withholds.

### 4.2 His identity, and the cache

His identity comes from two sources only, both his by construction: the
navigation bar's own photo (`img.global-nav__me-photo`) and the payload entity
whose `publicIdentifier` is his slug. It is held only as SHA-256 digests.
Only FULL name forms count as his. A first name alone does not, because in
"<first name> & N other connections work here" the first name belongs to a
connection. An encoded member id is read at its fixed 39 characters. That
was measured: server-driven component keys glue a section name straight onto
his id, with no separator, and a second id glued after it is still found.
