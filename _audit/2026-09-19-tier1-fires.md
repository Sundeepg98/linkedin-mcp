Fired 2026-09-19 17:44-17:55 by the box, on the operator's own account
(identity verified against the live session before the first fire), after he lifted the blanket
no-fire constraint in his own words: *"I'm not telling you not to fire it. Fire
it carefully when it is useful, and fire it safely."*

**Five fires. Every one verified on a surface DIFFERENT from the one clicked.
Nothing surprised me. Nothing reached another person.**

## WHAT HAD TO BE TRUE BEFORE ANYTHING FIRED

**Two preconditions were checked and one of them stopped the wave for ten
minutes.**

1. **The account is his.** `linkedin_auth_status` returned HTTP 200 against
   `voyager/api/me` and the member it named matched the operator. The value is
   not reproduced here -- the relation is what matters and the value is his.
2. **THE SERVER WAS RUNNING STALE CODE AND THAT IS A STOP.** It reported
   `stale: true` -- loaded from `ba78cdd2162d`, checkout at `5c5ebf9dda43`.
   **Measured rather than waved through:** the delta touches `writes.py` (13
   lines), `readonly.py` (32), `server.py` (168) and `dom.py` (52). **Firing a
   write through an unknown build of the write machinery is the exact class of
   surprise the stop conditions name.** Restarted via the shipped
   `scripts/restart_server.ps1` -- which says of itself *"Never touches
   Chrome"* -- and re-verified: no `stale_process` block.

**Writes are OFF by default** (`LINKEDIN_ENABLE_WRITES`). Enabling them is a
deliberate act and is recorded as one: the server was restarted a second time
with `-EnableWrites`, reporting `writes_enabled: true`.

## RUNGS 2 AND 3 -- `save_job` / `unsave_job`. THE MEMBERSHIP ROUND TRIP.

Target chosen on his real criteria rather than arbitrarily: **Node.js named in
the title, 3-7 years, TypeScript, REST APIs, queues, AWS, his own metro, a
product company.** A harmless test that is also useful beats one that is not.

    saved-tab count    1 -> 2 -> 1 -> 2
    prior state        established TWO ways: the tab did not contain it, and
                       the posting reported save_state not_saved
    each verification  read from /jobs-tracker/?stage=saved -- "a DIFFERENT
                       surface from the one clicked. A control that redraws
                       itself is the weakest possible witness to its own effect"
    label observed     Save -> Unsave -> Save, flipping with the state

**It is left SAVED**, deliberately: the job is a genuine match and discarding a
useful save to keep a test tidy is the wrong trade.

### AN EXPERIMENT I DECLINED, AND WHY

The gate names one thing it still cannot answer: *"whether re-saving restores
the original saved DATE, and therefore the list's order. Reversible in
membership is not reversible in ordering."*

**I could not settle it and did not pretend to.** The job had been saved sixty
seconds earlier, so an unsave-and-resave gives it a new date a minute later --
both hypotheses put it at position 1 and the test cannot distinguish them.
**The only version that WOULD answer it means unsaving his pre-existing save
and risking its place permanently.** That is a real cost for a cosmetic fact.
It stays unsettled and the gate stays right about it.

## RUNG 4 -- BLOCKED, AND THE BLOCK IS A FINDING

`follow_company` **refused, twice, identically**:

> *"the current state of this target came back 'unknown', so 'follow_company'
> cannot say which way it would move. **That is a refusal, not a delay** --
> proceeding here would be guessing."*

**The gate and my own criterion reached the same stop from different
directions** -- I had already concluded prior state could not be captured,
because both available sources report `unknown` and both say so explicitly:
the followed-Pages list is scroll-loaded and incomplete (*"a name missing from
`pages` is NOT evidence that the Page is unfollowed"*), and the posting reports
`company_follow_state: unknown`.

**IT IS NOT THIS POSTING.** Measured on a second, independent one -- Porter,
different company, 2 weeks old against 1 day, verified against promoted --
identical `unknown`, identical reason. **`linkedin_follow_company` follows FROM
THE POSTING PAGE, and the posting page renders no follow control for this
reader.**

### AND THE REPAIR IS VISIBLE IN THE SAME PAYLOAD

```
company_follow_state.state   unknown     <- what the gate reads, and refuses on
company_about.follow_state   "Follow"    <- POPULATED, on BOTH postings
```

**A second source on the same page read reports a state the gate treats as
unknown.** The About-the-company card carries a follow control and names its
state. That is a concrete direction source for a tool that currently has none
-- and the reason the gate does not use it should be established before anyone
wires it, because the designers chose the other control deliberately and this
document does not know why.

**This is the strongest kind of blocked rung: the capability is unreachable for
a measured, named, fixable reason rather than an unexplained one.**
