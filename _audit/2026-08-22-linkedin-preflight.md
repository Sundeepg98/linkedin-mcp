# 2026-08-22 - browser preflight, and a session_info that outlives the browser

**The line a missing browser now produces** (measured, env var unset, `linkedin_auth_status`):

> `browser_unavailable`: No Playwright browser executable at `C:\Users\Dell\AppData\Local\ms-playwright\chromium-1234\chrome-win64\chrome.exe`. PLAYWRIGHT_BROWSERS_PATH is unset in this server's own environment, so Playwright fell back to its default location. A stdio MCP server inherits ONLY the variables its client passes in that server's env block -- PLAYWRIGHT_BROWSERS_PATH being set in your user environment does NOT reach it otherwise, so check that before assuming the browsers are missing. Fix: if your browsers are installed elsewhere, add PLAYWRIGHT_BROWSERS_PATH to this server's env block in the client config and restart the client; only if they are genuinely not installed, run: `playwright install chromium`

1. **Reproduced exactly** before building: env var unset resolves the same C: path from the traceback, `exists=False`; set, it resolves `D:\dev-cache\ms-playwright\...\chrome-1234\chrome-win64\chrome.exe`, `exists=True`. The profile lock is now never taken on this path (verified live).
2. **One check could not cover it.** Measured: a HEADLESS launch ignores `executable_path` entirely and wants `chromium_headless_shell-1234\chrome-headless-shell-win64\chrome-headless-shell.exe`, whose path Playwright's Python API does not publish. So `preflight.assert_ready` checks what Playwright publishes and `translate_launch_failure` rewrites Playwright's own "Executable doesn't exist at X" for everything else -- no path is ever guessed, and every non-missing-executable error returns by identity so a timeout is never dressed up as a missing install.
3. **Gate order in `start()` is now flags -> preflight -> profile lock.** The flag boundary is the security invariant and depends on nothing outside the process; the lock is last because it is the only gate that writes to disk. A missing browser that had already taken the lock reports as "profile locked" -- true, and about the wrong problem.
4. **`linkedin_session_info` survives a dead browser.** `cookie_jar.py` reads a COPY of `_state/chrome-profile/Default/Network/Cookies`, never the live file, and never fetches `value`/`encrypted_value`. Live jar sha256 identical before and after (`edd891f2...4a131a`, 57344 bytes). It reports `li_at` expiring **2027-08-21T17:12:37Z, 364.4 days** with no browser at all.
5. **The honesty contract held, and got sharper.** `authenticated` still comes only from a real `GET /voyager/api/me`; offline it is `null`, never a cookie's presence. A separate `live_check` block carries `attempted` / `completed` / `why_not`, and `attempted` now distinguishes "I tried and the browser is broken" from "you asked me not to try" (`verify_live=False`).
6. **Two defects found by mutation testing, not by review.** The `verify_live=False` guard could not fail -- its trap raised inside `BROWSER.session`, which the tool catches on purpose, so it passed against a mutation deleting the branch it guarded; replaced with an external call recorder. And the fallback reported `attempted:false` after genuinely trying. Both fixed in `oldsha21`.
7. **Guards shown failing: 8 mutations, 8 caught** -- message drops the env var (6 tests red), translate rewrites everything (1), headless claimed verified (1), preflight moved after the lock (1), a cookie promoted to `authenticated` (5), `verify_live` branch deleted (1), fallback lies about attempting (2), jar query fetches `encrypted_value` (20). Read-only allowlist, AST/source scanners, tool-surface and launch-flag boundary all unweakened and green.
8. **579 -> 650 tests, all passing.** Commits `oldsha03`, `oldsha21`, pushed. Nothing outside `linkedin/`; no `*_login*` or `linkedin_notifications` call made; no config file touched.
