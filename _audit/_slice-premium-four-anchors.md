## 1. Two defects found and fixed in this slice's own instrument

**A. HTMLParser.getpos() drifted on the real search-appearances capture.** A
single `<img>` tag's attributes did not fit `check_for_whole_start_tag()`'s
quoting assumptions, so it returned an end position 9 characters short of
that tag's true end (confirmed by direct character-offset comparison against
the raw bytes, not inferred). The tag was still correctly recognised (right
name, right 3 attributes); only the position bookkeeping broke, and it then
stayed broken: 29 of 29 anchors past that point on that capture were off by
2-54 characters, monotonically non-decreasing. Fix: raw_offset is no longer
read from getpos(). `_independent_anchor_offsets()` finds every real `<a`
tag-open by forward regex search over a copy of the document with every
`<script>/<style>/<code>/<template>/<noscript>` block blanked to spaces of
the same length (position-preserving, so every other offset is unaffected).
HTMLParser's own tag/CDATA recognition and this independent search are
cross-checked by COUNT before either is trusted; a mismatch raises rather
than guessing. Control 4 below manufactures exactly that mismatch and proves
the cross-check fires, then proves the script recovers cleanly afterward.

**B. The original brief's capture path was hardcoded into a .py file and
tripped this repository's identity guard** (the operator's own name is a
`[drive root]` shape it refuses at commit time, scanning untracked files
too). Flagged by the wave lead's disk downlink mid-slice (`_TEAM_LEAD_
premium_four.md`, read, applied, and deleted per its own instruction).
Fixed: the default `--state` is now derived as
`Path(__file__).resolve().parents[1] / "_state"`, never a literal path.
Re-verified clean with `scripts/staged_identity_shapes.py` after the fix
(exit 0, "9 file(s) examined, no undeclared shape").

## 5. Raw-vs-rendered discipline, per prefix

Two independent countings are reported for a reason: an href-WRAPPED count
(only counts `href="..."` occurrences, absolute or relative) and a
BARE-WORD count (matches this repository's own "inmail" convention -- no
attribute context required). They answer different questions and can
legitimately disagree.

| prefix | raw (href-wrapped, summed over 6) | parsed (summed over 6) |
|---|---|---|
| /analytics | 4 | 4 |
| /jobs/collections | 2 | 2 |
| /premium | 12 | 12 |

No gap on any of the three prefixes by the href-wrapped measure: every
href-shaped occurrence of these addresses in these six documents is a real
drawn anchor; none is bundle-only, counted this way.

The bare-word measure tells a different, complementary story (see section 3
per-route for the exact numbers): "profile-key-skills" and "recruiter-views"
are distinctive enough that their bare-word counts closely track their real
anchor counts (one exception -- profile-key-skills carries one bundle-only
occurrence on search-appearances, reconciling with commit fce0843). "top-
applicant" and "top-choice" are NOT distinctive as bare words -- both
double as ordinary job-card badge text used across the job-search surfaces
independent of the /jobs/collections/ route, so their bare-word counts (8-10
per capture, including on captures with zero real anchors) measure the UI
vocabulary, not the route. Bare-word census is only as good as how unlikely
its needle is to occur elsewhere in ordinary page copy.
