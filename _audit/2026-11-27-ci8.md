## 1. The full matrix on a lane's ref: `lane_ci.py wait <sha> --full`

### 1.1 What it does

`.github/workflows/ci.yml` already gave a `workflow_dispatch` on a `ci/` ref the full matrix, three cells by
six shards; only a PUSH to `refs/heads/ci/*` takes the fast lane, and `tests/test_ci_fast_lane.py` pins both
shapes. What was missing was a command that runs it safely and reads it by sha. `scripts/lane_ci.py wait
<sha> --full` does it in five steps (the module docstring has them in full):

1. It refuses unless `origin`'s `ci/<branch>` holds exactly `<sha>`, read with `git ls-remote`. A dispatch
   runs the ref's head, so a full matrix of another commit would carry this sha's name.
2. It waits for the PUSH run of `<sha>` on `ci/<branch>` to finish. The dispatch shares its concurrency group
   (`ci.yml` keys a branch's group on its ref, with cancel-in-progress), so whichever started first would be
   cancelled. A red push run ends it there, and nothing is dispatched: the full matrix cannot certify a sha
   whose lane run is red, and it would spend eighteen jobs of the shared pool to learn so.
3. It reads the dispatch runs of `<sha>` on the ref BEFORE dispatching. One still running is waited on and
   never sent again, because a second dispatch would cancel it through the same group. One already
   finished is read and not repeated: it is the full matrix's verdict on this sha. Only none, or a cancelled
   one, sends `gh workflow run ci.yml --ref ci/<branch>`.
4. It finds the new run by head sha, event and ref, and excludes every run id that existed before the
   dispatch. It never reads "the latest run", which right after a dispatch is somebody else's. It waits on
   the run for up to 45 minutes; master run 46042146411 took 10m44s.
5. It reports the verdict and every cell: each cell's shards and their conclusions, the plan and totals
   jobs, and on a red run the failing tests, the way `wait` prints them. A green run of one cell is the fast
   lane's shape. It is reported as NOT THE FULL MATRIX, never as the full matrix's certificate.

Re-running it after a shell cut the wait short is therefore safe: it finds the dispatch it already sent.

`cmd_wait`'s polling loop moved into `_await_run`, with the same output, so the 58 existing tests pass as
they were.

## 2. Every shard records the runner it ran on

### 2.1 Why

Master run 46030101439's windows shard 1 stalled in its parallel phase and passed on the re-run. Lane
masterfix7 could read the stall only from junit durations (its record, section 4, and its Q2), because no
shard job recorded how many xdist workers `-n auto` had started, how many CPUs the runner had, or how much
memory was free. That is the measurement `_audit/2026-09-21-the-windows-shard.md` asked for in its 7.1.

### 2.2 What it records

ONE step per shard, "What this runner has, before the run", placed after the install and before the run:
`python scripts/ci_runner_facts.py --out runner-facts.json`. It is stdlib only.

- **`xdist_workers`**: what `-n auto` starts in that job. It is asked of xdist's OWN resolution, the
  `pytest_xdist_auto_num_workers` hook, in the job's interpreter and environment, and never re-derived beside
  it. The rule moves with the install: with psutil, xdist counts physical cores, and without it, the CPUs the
  process may use. `PYTEST_XDIST_AUTO_NUM_WORKERS` overrides both. `xdist_rule` names the branch that
  applied. No conftest here implements the hook, so xdist's is the one the run calls.
- **`cpu_count`** and **`cpus_usable`**: the logical CPUs, and the ones the process may run on, where the
  platform says (`os.process_cpu_count` from 3.13, `os.sched_getaffinity` on Linux).
- **`memory_total_bytes`** and **`memory_available_bytes`**: `/proc/meminfo`'s MemTotal and MemAvailable on
  Linux, and `GlobalMemoryStatusEx` on Windows.

A fact it cannot read is recorded as unknown, with its reason, and never as a zero or a failure. It prints
one `runner:` line in the job log and writes `runner-facts.json`. `ci_shard_totals.py record --runner` carries
the file into the shard's report as `runner` (null when it is missing, because the report step runs
`if: always()`), and `verify` prints every shard's runner beside its siblings'.

Measured on this box (VERIFIED, the script's own output):
`runner: 8 CPUs (8 usable); -n auto starts 8 workers (no psutil: os.cpu_count()); memory 18.5 GiB available of 31.7`.
Under py3.10 the usable count is unknown, because Windows before 3.13 has neither API, and the line says
so. The runners' own lines are in section 8.

## 5. The tracker wait's "999 < 1000 ms" flake

### 5.1 The flake (VERIFIED, net7's record, section 11)

Lane CI run 45970717983, attempt 1, ubuntu py3.13:
`tests/test_tracker_readiness.py::test_the_empty_tab_rule_absorbs_load_and_still_catches_the_ceiling`
asserted `waited_ms >= 1_000` on a 1000 ms bound, and the runner read 999. Attempt 2 passed.

### 5.2 The mechanism

Two clocks meet in that assertion, and the test held neither (DERIVED, from the driver's code and the product's):

- **Playwright's driver ends the wait.** In the installed driver (Playwright 1.63.0, its bundled progress
  controller), the deadline is set when the call arrives, as its monotonic time plus the timeout, and a
  Node timer is armed for what is left of it. Node's timers run on the loop's whole-millisecond
  clock, floored, so the timer is due when that clock has moved on by the bound. In real time, that can be
  up to one millisecond sooner: anywhere in the bound's last millisecond.
- **The product reads the wait** around the whole round trip, on `time.monotonic()`, and truncated the
  reading with `int(...)`. A wait that really lasted 999.6 ms read 999, and the note printed
  "999ms, the full bound": a sentence contradicting its own number.

The bracket around the round trip always holds more than 999 ms of real time on a 1000 ms bound, so a
reading rounded UP to the whole millisecond cannot fall short. There is a second, latent fault: under
Python 3.10 on Windows, `time.monotonic()` is GetTickCount64, at 15.625 ms resolution, while
`time.perf_counter()` is QueryPerformanceCounter on every version (VERIFIED, `time.get_clock_info` on this
box under 3.10.19 and 3.13.14). A reading taken on the tick clock can fall a whole tick short. No CI cell runs
Windows with 3.10, so it was never seen to fire.

The box cannot show the flake naturally. 200 timeouts of the real wait at a 100 ms bound read 100.02 ms
at the least (VERIFIED, the lane's tick probe, in its scratch): this box's timers fired late every time,
where the ubuntu runner's fired early once.
Before the fix, the two bound tests passed 5 of 5 under py3.10 here as well.

### 5.3 The fix, at the cause

`dom.wait_for_tracker_list` reads its duration on `time.perf_counter()` and rounds it up:
`math.ceil((time.perf_counter() - started) * 1000)`. Nothing else changes, and nothing is retried or
widened. The same file holds a second exact-bound assertion (`test_the_shell_is_a_finding_and_says_so`,
`waited_ms >= 300` on a 300 ms bound). It had the same exposure, and it is covered by the same fix.

### 5.4 Reproduced deterministically, then held (VERIFIED)

Section 2b of `tests/test_tracker_readiness.py` replaces the product's `time` module with a script of real
instants. Its `monotonic()` can be quantised to 15.625 ms ticks, and its `perf_counter()` is always fine. The
page's wait raises Playwright's own `TimeoutError`, the class the product classifies a timed-out wait by.
There is no browser and no sleep.

| test | before the fix | after |
|---|---|---|
| `test_a_wait_the_driver_ended_never_reads_short_of_its_bound[999.0001]`, `[999.6]`, `[999.9999]` | 3 failed: `waited_ms` 999 each | passed |
| `test_the_wait_is_read_on_the_fine_clock_not_the_tick_clock` (300.8 ms read as 19 ticks) | failed: 296 | passed |
| `test_the_note_prints_the_full_bound_beside_a_wait_that_spent_it` | failed: "(999ms, the full bound)" | passed |

Mutants: truncating again (`int`) killed 4; reading `monotonic` again killed 1; both by FAILED.

## 10. Lessons

1. A WHOLE-MILLISECOND TIMER AND A TRUNCATED READING MEET AT THE BOUND. The driver's clock can end a wait in
   the bound's last millisecond of real time, and `int()` then reads the bound minus one. A reading that a
   lower bound is asserted on is rounded up. A short duration is read on `perf_counter`, because
   `monotonic` is a 15.625 ms clock on Windows before Python 3.13.
2. A FLAKE THE BOX CANNOT SHOW CAN STILL BE REPRODUCED. When this box's timers only ever fired late, scripting
   the clock the product reads, and raising the error the driver raises, turned a one-in-many ubuntu flake
   into five deterministic failures.
3. A WINDOW OVER A GROWING CELL IS A TIMER. A guard that reads N characters of prose fails when a neighbour
   grows, and it matches words wherever they fall. Locate the claim by structure, then read that claim.
4. A GREEN RUN IS NOT A CERTIFICATE OF A SHAPE. One cell, green, is the fast lane. Read the shape from what
   ran, and hold the shape check to the plan step's own outputs.
5. A SPLIT KEEPS THE OLD MODULE AS THE ADDRESS. The names other files import stay where the imports point,
   so the split touches none of the 69 importers. Each name moves with its own comment and nothing else.
6. A STALE TABLE IS REBUILT BY ITS RECIPE, NOT EDITED. When the run that priced a file is gone, re-attribute
   a newer run's testcases to the files they now live in, and say so in the label.
