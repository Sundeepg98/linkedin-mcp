## 2. The settings7 provenance tests on a CRLF checkout: DETERMINISTIC

### 2.1 The mechanism, measured on this box

This box checks out the way the windows cell does (VERIFIED, `git config --show-origin`): the system
gitconfig of Git for Windows sets `core.autocrlf=true`, and the repository has no `.gitattributes`.
`git ls-files --eol` over the tracked set reads `i/lf w/crlf` for all 1387 text files: LF in the
index, CRLF in the worktree. 5 files carry no line end at all, and none is `i/crlf` or mixed. The five
fixtures' committed blobs hold 0 CR bytes and 0 non-ASCII bytes. Read raw from a fresh checkout here,
they hold one CR per LF.

Both provenance tests read the fixture with `read_bytes()`, decode it as ASCII, and compare it with an
LF literal. On a CRLF checkout they fail, and on an LF one they pass. Every other test in the two
files reads with `read_text()`, whose universal newlines take CRLF to LF, which is why 17 passed
beside them. Reproduced locally before any change: 5 failed and 17 passed, exactly the five CI tests.

### 2.2 Why the fix is in the test and not a `.gitattributes`

A `.gitattributes` pinning LF would make every checkout LF, and the windows cell would then no
longer measure the line-ending difference. That difference is one of the three reasons
`.github/workflows/ci.yml` gives for keeping a windows cell at all ("the core.autocrlf line-ending
difference the vendored-drift comparison normalises away"). The repository has met this before and
answered it in the comparison, not in the checkout. Five test files normalise before they compare
bytes (`tests/test_first_contact_message.py`, `tests/test_named_profile_live_skeleton.py`,
`tests/test_people_search_names.py`, `tests/test_profile_views_skeletons.py` and
`tests/test_search_vertical_fixtures.py` each define `_lf`), and the audit-index and blocker-map
generators do the same. Pinning the checkout is a matrix decision, and it is not this lane's to
make. The expectation the two tests made, that the bytes on disk are LF, is what the repository's own
checkout regime does not promise. So the test changes, and its intent stays whole: the opening and
the strict-ASCII decode are both still asserted, on the raw bytes.

### 2.3 The fix

`_as_committed(raw)` in `tests/test_live12_settings_word_fixtures.py` decodes the raw bytes as strict
ASCII (any other byte still raises) and reads CRLF as LF. `_assert_opens_with_its_provenance(text,
builder)` holds the opening and the builder's name. Both provenance tests use them, and
`tests/test_live11_settings7_word_fixture.py` imports them, as it already imports that file's token
helpers.

The test that fails without the fix: `test_a_crlf_checkout_of_each_fixture_opens_the_same` (one per
fixture) and `test_a_crlf_checkout_of_the_fixture_opens_the_same`. Each takes the fixture's bytes as
committed (LF, asserted to hold no CR), writes each LF as CRLF the way `core.autocrlf` does, and holds
the result to the same check. Because it renders the CRLF checkout itself, it fails without the fix
on an LF checkout too, so lane CI's ubuntu cell can see this class.

## 3. The group composer's zero-poll test: A RACE, fixed at the race

### 3.1 Not deterministic

The same commit and shard plan passed on attempt 2 (VERIFIED, job 140619870536). Lane msg7 met the
same test failing in its lane CI run 45972966471 on ubuntu py3.13, and passing in its run 45963048709
and locally; its record lists it under items for others, item 4, as a timing premise outside its
diff. Attempt 1 of shard 0 also ran 1.67 times slower than attempt 2 (276 s against 166 s).

### 3.2 The mechanism (DERIVED from the code, then shown in 3.4)

- The world (`tests/group_composer_worlds.py`, config `enableAfterMs: 120`) turns Post on with
  `setTimeout(turn, cfg.enableAfterMs)` inside the editor's `input` handler. The act's fill is one
  `page.fill`, so the timer starts when the words land.
- With `POLLS` at 0, `group_composer.wait_for_post_enabled` takes one `read_composer` and returns.
  Then `writes.py` hands `group_composer.post_gate` a FRESH `read_composer`, and that reading decides.
- `read_composer` is up to seven Playwright calls: four counts, Post's count, Post's `is_enabled`,
  the Schedule count, and with text, the editor's `inner_text`. The deciding `is_enabled` is the
  eleventh call after the fill returns.
- So the test passes only while eleven round trips finish inside 120 ms of page time. On a starved
  runner they do not, Post reads on, the gate proceeds, and `proceeded is False` fails.
- The composer variant (`openAfterMs: 120`) has the same shape: the deciding counts are the seventh
  and eighth calls after the trigger's click returns.

### 3.3 The fix: the test holds the page's clock

`_refused_without_the_wait` (shared by the original test and the new one) installs the page's clock
and pauses it before the first world loads (`page.clock.install(time=0)`, `page.clock.pause_at(1)`,
in seconds as the Python API takes them). The world's timers then cannot fire on the runner's clock,
however long the readings take. After the receipt, the helper runs the clock on by the world's own lag
(`page.clock.run_for(120)`, in milliseconds). It then asserts that the composer is drawn, or that Post
is on. So the refusal is the missing wait's, and not a world that never arrives.

The premises, probed first in a local Chromium (`clock_probe.py`, section 5):

- without the clock, half a second of real time fired both 120 ms timers;
- with the clock installed and paused before content, the timers held through two `set_content`
  calls, a click and a fill, and the half second;
- `run_for(119)` fired neither, and one more millisecond fired both.

Playwright's own waits run outside the page's main world and were not affected. `page.clock`
arrived in Playwright 1.45. This box runs 1.63.0 and CI resolved 1.65.2.

## 8. Lessons

1. A BYTE READ OF A COMMITTED FILE IS A READ OF THE CHECKOUT. On this repository's Windows cell the
   same blob arrives as CRLF. A test that compares raw bytes with an LF literal passes on ubuntu and
   on every lane, and fails only on master's windows cell. Read the line ends as committed, or render
   the CRLF checkout in the test itself so ubuntu can see it.
2. A LOCAL RED THAT "ONLY THIS BOX" SHOWS IS THE WINDOWS CELL'S RED. This box and the windows cell
   share `core.autocrlf=true`. Before a local CRLF failure is filed as a property of the box, the
   windows cell is the place it will recur.
3. A ZERO-WAIT TEST AGAINST A TIMED WORLD IS A RACE WITH THE RUNNER. Whether the deciding read lands
   before a page timer is a property of the runner's speed. Hold the page's clock (`page.clock`), and
   prove the world is late, not dead, by running the clock on afterwards.
4. EMULATE THE SLOW RUNNER TO GET A DETERMINISTIC RED. Holding every reading back by more than the
   lag turned a 1-in-many CI flake into 2 of 2 failures locally, and it found the composer variant's
   race, which had never failed on CI.
5. ATTEMPT 1 AGAINST ATTEMPT 2 IS THE DISCRIMINATING INSTRUMENT. Same commit and plan. The per-file
   ratio of summed test time showed the degradation was selective (2.5x to 10x on four
   process-spawning files, about 1x elsewhere), and that rules out the code before any code is read.
6. A MUTANT CAN BE WRONG IN THE DIRECTION OF A MISSED CHECK. `a or b - 1` is `a or (b - 1)`. When a
   mutant kills fewer cases than it should, read the mutant before the check.
