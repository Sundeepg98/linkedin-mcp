## 1. THE FINDING: THE LEDGER BROKE ITS OWN ASSIGNMENT RULE ON FIVE OF THESE SIX

The ranked table states its own rule: *"one blocker per row, the EARLIEST
binding constraint. A row that looks blocked by a missing write but has no way
to find its target is filed against the missing surface, not the missing
write."*

Measured against `writes.WriteSpec`, five of these six rows are filed against a
missing write when the earliest binding constraint is a page nobody has opened.

`WriteSpec.url_template` is `Optional[str]`, and the field's own contract says
why:

> `None` where the surface has NEVER BEEN LOADED. A gate may not name a target
> surface nobody has opened, for the same reason it may not print an unmeasured
> reversibility claim.

So for every one of these blockers, a WriteSpec cannot be completed until the
surface is photographed. **The `3*W` the cost model charges for "a new WriteSpec
+ gate + consent text" cannot be spent first.** It is not the earliest
constraint; it is not even a reachable one.

    ledger queue        measured earliest constraint
    36  BUILD       ->  MEASURE  (and a boundary ruling, see section 3)
    61  BUILD       ->  MEASURE
    62  BLOCKED     ->  MEASURE  (and it is NOT blocked on a boundary, see 3)
    65  MEASURE     ->  MEASURE  (confirmed, and it is the cheapest of the six)
    70  DECIDE      ->  DECIDE   (confirmed, and the decision changes, see 5)
    81  BUILD       ->  MEASURE

**This is not a criticism of the classifier's reasoning; it is a consequence of
its inputs.** The ledger was built from the census row TEXT. The constraint that
actually binds lives in a dataclass field in `writes.py`. Nothing in the row text
could have surfaced it.

## 2. THE MECHANISM THESE SIX ROWS NEED IS ALREADY BUILT, COSTS NO BOUNDARY, AND IS CURRENTLY EMPTY

`writes._NINE_REFUSALS` is a registry mapping an action to a refusal sentence
that names its own blocker. Its header defines exactly two blocker shapes and
forbids either standing in for the other:

    NO CONTROL  -- the thing that would be clicked has never been observed.
                   A capture lifts it.
    NO SURFACE  -- the address the action would act on is refused by
                   readonly._FORBIDDEN_URL_SUBSTRINGS, which is checked before
                   the allowlist and is NOT shortened for a write.

Those are precisely the two shapes my six blockers occupy, and the surrounding
comment records that building the original nine widened no boundary at all:
*"the four frozen denylists are byte-identical across this change, and that is
checkable rather than asserted."*

**MEASURED AT THIS TREE: `len(_NINE_REFUSALS) == 0`.** Every one of the original
nine has left the table, each departure documented in place as a comment. The
consumer at `writes.py:5548` -- `if spec.action in _NINE_REFUSALS:` -- therefore
cannot fire in the current tree.

Two things must be said about that, and they are different claims:

1. **The empty state is CORRECT.** The table emptied because the work got done:
   actions left by shipping, or by having their blocker ruled on. Nothing here
   is a defect and nothing needs reverting.
2. **A pointer to it has gone stale.** `writes.py:971` reads *"The blockers are
   itemised per action in `_NINE_REFUSALS`."* At this tree it itemises nothing.
   That is a standing instruction rather than a dated note -- this wave followed
   it and reached an empty dict -- and it is the class this repository has
   already recorded as the one the correction machinery cannot bind.

**I DID NOT FIX THAT SENTENCE.** `git log --oneline -3 -- linkedin_server/writes.py`
names `0e98882`, `1a3527f`, `7d785e5` -- the uploads, latency and comment waves.
It is not my artifact and today's rule is that a neighbour's lines are not mine
to sweep. It is recorded here for whoever holds that file.

**The consequence for the roadmap is the useful half:** the honest first
deliverable for the write rows in these six blockers is not six WriteSpecs. It is
six `_NINE_REFUSALS` entries, each naming NO CONTROL or NO SURFACE and the exact
capture or ruling that lifts it -- a shape this package has shipped before, at
zero boundary cost, where `mint` refuses a grant at ISSUE so the operator reads a
warning rather than an offer he cannot act on.

## 3. THE BOUNDARY, MEASURED RATHER THAN DERIVED

New instrument, committed with this document:

    scripts/_probe_jobs_tail_boundary.py

It opens nothing. It calls the shipped `readonly.assert_read_url` on candidate
address strings that are literals typed into the file, and reports, per address,
the RELATION plus the forbidden substring that bit -- because a refusal naming
only what it did NOT match is half a measurement.

**IT WAS SHOWN FAILING BEFORE IT WAS BELIEVED, and it failed on its first run
against its own author.** The control block asserts one known-ALLOW and one
known-REFUSE address before any measurement is taken. On the first run it printed

    CONTROL FAILED: control-allow: the job search surface this server reads today
      expected ALLOW, predicate said REFUSE

because I had called a predicate name that does not exist in this package. The
probe refused to print a single measurement. Had the control not been there, all
19 candidates would have come back REFUSE and I would have reported the boundary
as far tighter than it is.

### Three ledger entries are wrong, and one is wrong in the expensive direction

**62 TRACKER-ROW-MENU -- the ledger charges `denylist x1`. There is no URL
denylist cost at all.** Both tracker stages the row menu is drawn on are ALREADY
ADMITTED:

    ALLOW  https://www.linkedin.com/jobs-tracker/?stage=saved
    ALLOW  https://www.linkedin.com/jobs-tracker/?stage=applied

The census prose the charge came from (`_audit/_census/jobs.md`, the rows 54-56
note) says `"update"`, `"set"`, `"add"` are on the **mutation-verb denylist**.
That is a different list from `readonly._FORBIDDEN_URL_SUBSTRINGS`, and the
ranked table's column is headed `boundary`, which reads as the URL boundary.
**Two different lists were collapsed into one column.** Row 62's boundary cost is
zero and its queue is MEASURE, not BLOCKED.

**36 JOB-ALERTS-SURFACE -- the ledger charges `denylist x1`. Measured, three

    REFUSE  an alert delete verb           forbidden substring: '/delete'
    REFUSE  an alert create verb           forbidden substring: '/create'
    REFUSE  alert frequency/channel        forbidden substring: '/settings/', 'settings'

The bare token `settings` is on the forbidden tuple, which is checked BEFORE the

allowlist. Exemptions in this package are exact-url tables compared with `==`,
never as a shape, so the real cost is one exemption per exact address rather than
one denylist edit. **This is the entry that is wrong in the expensive direction:
the ledger costs `A=1, D=1` where the measured floor is higher.**

## 4. THE PAGE-SIZE DEFECT: WHAT I CHECKED AND WHAT I DID NOT

The brief carried a defect measured today: `linkedin_search_jobs` returns a
window of **SEVEN**, not 25, and `start` offsets by **ONES** -- seventeen live
loads, seven every time, against a LinkedIn-reported count of 2915. The docstring
is fixed for that one tool.

A census of every other page-size, pagination and offset-stride assumption in the
tracked package was commissioned as a separate read-only slice, with the two
classes kept apart deliberately: a LISTING-WINDOW assumption is a claim about
LinkedIn and can be wrong; a caller-side cap this server applies to its own output
is a server choice and is not wrong. **See section 7 for its disposition. I do
not report its numbers here, and no result of it is asserted anywhere in this
document.**

What I can say from my own reading: **none of my six blockers' rows carries a
page-size assumption of its own**, because none of them has a reader at all.
Every one is a write or an unopened surface. The inheritance risk in this slice
is zero, and that is a statement about the absence of readers rather than about
the correctness of any number.

## 5. EASY-APPLY-MULTISTEP: THE RULING IS REAL, AND IT IS NOT THE ONE THE LEDGER FRAMES

The ledger files row 70 as DECIDE with "ruling needed". Measured, the row is not
unbuilt and the boundary is not what stops it.

Both address spellings refuse at the substring gate:

    REFUSE  .../jobs/easyapply/<id>/    forbidden substring: 'easyapply'
    REFUSE  .../jobs/easy-apply/<id>/   forbidden substring: 'easy-apply'

**But the shipped `apply_job` does not use either address.** It clicks a control
on `/jobs/view/<id>/`, which is admitted, and LinkedIn draws the flow as a modal
over the posting. So the forbidden substrings are not the blocker.

The blocker is a deliberate, documented refusal. `linkedin_apply_job` submits
only if all of: the modal rendered; exactly one control carries LinkedIn's own
submit hook; that control is visible and enabled; its name corroborates the hook;
and **zero advance controls are present**. Its docstring states the reason
plainly: *"filling in steps that have never been seen, to reach a submit that
cannot be withdrawn, is the one guess this server does not make."*

**THE DECISION THE OPERATOR ACTUALLY FACES IS NOT "SHOULD MULTISTEP APPLY BE
BUILT". IT IS "MAY A DRAFT BE SPENT TO PHOTOGRAPH THE MODAL".** Here is why, and
it is the part the ledger's framing hides:

* the multi-step modal has **never been observed on this account** -- the
  docstring records exactly one apply flow ever seen, a single screen with one
  enabled submit and no Next;
* the modal is drawn only **inside the confirmed path**. There is no
  modal-preview mode: calling `apply_job` without a token reads the posting, not
  the modal;
* and `writes.py:7967` records the cost of opening it: *"the first click opened a
  modal and may leave a draft in his job tracker."*

So the capture that would unblock this row costs a DRAFT ROW, not an application.
That is a materially smaller and more decidable question than the one the ledger
poses, and it is decidable partly because the draft is observable: the tracker's
`draft` stage is one of the three admitted stages and this repo already holds a
capture of it.

**A design that follows from this, NOT built and NOT proposed as a write:** a
read-only apply-modal reader -- open the control, read the modal, close it,
submit nothing -- would photograph the multi-step flow, and would ALSO let him
see a posting's screening questions before committing to an application that
nobody has established LinkedIn lets him withdraw. That is directly useful to a
Node/TypeScript hunt where screening questions decide whether an application is
worth the credit of his time. **It is not free and this document does not pretend
it is: it leaves a draft, which is a state change on his account, and it is
therefore the operator's ruling and not mine.**
