### AND I MET THE REFUSAL'S OWN ESCALATION CONDITION

The refusal predicts its own failure mode and names what would falsify it:

> *"MEASURED 2026-09-02: two calls seconds apart returned absent then present,
> so the parameter does not ride on every redirect. Try again; **if it keeps

> **A refusal that names the observation which would overturn it is worth more

## GROUND 2 -- THE SERVER WENT STALE *DURING* THE WAVE, AND THE DELTA IS NOT CODE

**This is the finding I did not expect and it is the one worth keeping.**

    17:52:0x   linkedin_auth_status            NO stale block   -> not stale
    17:53:5x   profile_editor_fields           stale: true
               loaded_commit  5c5ebf9dda43
               disk_commit    70d7c0f62e97
               process_started_at  2026-09-19T12:12:23Z (17:42 IST)

The process was **not** unrestarted -- 17:42 IST is Tier 1's own restart. The
checkout moved underneath it while I worked.

**Absence of the block is a POSITIVE reading, not a silence.** `server.py`
`_announce_staleness` returns the answer untouched only when `stale is False`;
`None` ("cannot tell") is still announced. So my 17:52 check was a measured
not-stale, and the 17:53 read was a measured stale. **Both readings are
correct. The state changed between them.**

### WHAT THE DELTA ACTUALLY CONTAINS

    git diff --stat 5c5ebf9dda43 70d7c0f62e97
      _audit/2026-09-19-tier1-fires.md | 142 +++++++++++++++++++++++
      1 file changed, 142 insertions(+)

**One markdown file. Zero Python. Zero lines of write machinery.** It is the
Tier 1 wave committing its own audit, which I watched land mid-wave.

> **THE STALENESS DETECTOR MEASURES COMMIT IDENTITY, NOT BUILD IDENTITY.** In a
> tree with several writers, a neighbour committing a document flips `stale:
> true` on a process whose loaded Python is provably identical to disk.

**Tier 1's stop on staleness was RIGHT and mine is a different case.** Its
delta was `writes.py` 13 lines, `readonly.py` 32, `server.py` 168, `dom.py` 52
-- the write machinery itself, which is an unknown build by any reading. Mine
is prose.

### AND I AM NOT RULING THAT IT IS THEREFORE SAFE TO FIRE

I can show the loaded build is byte-identical to disk on every executable path.
**I am still not firing through a red stop condition on that argument**, and
the reason is recorded in this campaign twice already:

> *"It would be CONVENIENT for me to declare six foreign reds green."*

A stop condition I talk my way past because I measured the exception is the
same act as declaring a foreign red green. **The correct disposition is: the
stop held, the wave did not fire, and the detector should be sharpened so the
next wave is not asked to make this judgement at all.**

**PROPOSED, NOT DONE:** compare a hash over the loaded MODULES against disk,
or exclude non-importable paths from the comparison, so `_audit/` churn cannot
flip a write gate. That is a design change and it belongs to whoever owns
`_staleness()`, not to a wave that wanted it to be true.

### A CONSEQUENCE THAT OUTLIVES THIS WAVE

**A precondition checked once is not a precondition held.** Tier 1 verified
not-stale before its first fire and fired five times after. On a tree this
busy, the check and the fire are different moments and the state moved between
mine in about ninety seconds.

> **Staleness is not a gate you pass. It is a reading with a timestamp, and on
> a shared tree it expires while you work.**

## GROUND 3 -- THE AUDIENCE IS UNMEASURED, SO "MINIMUM AUDIENCE" CANNOT BE CHOSEN

The brief's instruction was **"CHOOSE THE FIELD FOR MINIMUM AUDIENCE ... A
profile field is VISIBLE -- unlike Tier 1, this one has an audience."**

The spec's own `residue` says the audience is not knowable from here:

> *"HIS PROFILE IS WHAT RECRUITERS READ, and it is read continuously rather
> than at a moment he chooses ... An edit that is reverted an hour later was
> still live for an hour. And **LinkedIn notifies a network about some profile
> changes, which is a broadcast this server has not measured and would not
> control.**"*

**Tier 1 Rung 1 could write `AUDIENCE: NOBODY` because `update_setting`'s spec
establishes it. This spec establishes the opposite: an unmeasured, uncontrolled
broadcast.** There is therefore no measured basis on which to call any field
the minimum-audience one -- the ranking the brief asked for does not exist yet.

**And the enumerator refuses (Ground 1), so I cannot even list the candidates.**
The brief's non-firing condition is met a fortiori: I cannot show that some
field is unobtrusive, because I cannot show what the fields are.

### RESTORATION WOULD NOT HAVE BEEN RESTORATION

Worth stating because the brief's step 4 assumes it. The spec is explicit:

> *"putting that string back through this server is **A SECOND EDIT rather than
> an undo**: whatever the field's history records, it records both changes."*

`reversibility_measured=False`, `reversibility_class: STILL-UNKNOWN`, and what
remains unmeasured is named precisely: whether LINKEDIN offers an undo of its
own has never been looked for. **Reading the old value back is not LinkedIn
restoring it.** A clean read-back would have proved the value returned, not
that the edit was undone.

Measured by importing the module rather than by reading it:

    PERFORMABLE size                         12

    registered & non-performable             ['linkedin_set_open_to_work']

The frozenset admits it ~3600 lines below, as **"THE ELEVENTH, 2026-09-02, on
the operator's ruling 'I want all capabilities'"**. Both sentences were written

(addressed but not yet permitted) that the same day's later edit superseded.

### THE TEST CARRIES THE SAME STALE STATE, AS AN EXEMPTION THAT CANNOT FIRE

`tests/test_writes.py` loops over registered-but-NOT-performable specs and
carves one name out by hand:

    if spec.action != "update_profile_field":
        assert spec.url_template is None, name

with the comment *"given its url under an exact-url exemption while staying
firmly outside PERFORMABLE."* **The loop's set is `{linkedin_set_open_to_work}`,
so the carve-out is unreachable** -- measured, `carve-out reachable: False`.

**AND THE HONEST HALF, WHICH POINTS THE OTHER WAY:** a dead exemption makes the
assertion STRICTER, not weaker -- `url_template is None` now runs
unconditionally on every member of the loop. **This is documentation decay and
a check that cannot fire, NOT a safety hole, and inflating it into one would be
the mirror of the error this campaign keeps recording.** The repo's own second
law is why it is worth writing down at all:

> *an instrument enters only if it has been shown failing; a check that cannot
> fail certifies nothing.*

**NOT REPAIRED BY ME.** Three artifacts must move together -- the spec comment,
the test's carve-out, and whatever prose cites the negative control -- and a
`tests/` edit fires the ~60s boundary hook on a tree with live writers. **It is
a clean, closed slice for a successor: delete the carve-out, correct the spec
comment to say the action IS permitted, and confirm the negative control the
comment promises still exists and can still fail.**
