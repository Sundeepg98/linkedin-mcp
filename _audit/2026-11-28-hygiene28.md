### 2.2 Which file it edits now

- `--file PATH` edits exactly PATH.
- With no `--file`, it edits `_audit/INSTRUMENTS.md` under the git root of the directory it is RUN FROM
  (`git rev-parse --show-toplevel`), never under the tree it is stored in.
- Its first two lines name the file and say which checkout holds it.
- A file the MAIN checkout holds is refused (exit 2, nothing written) unless `--main-checkout` is passed.
  The flag only permits; it never chooses the main checkout's file. `merge_wave.py` resolves the main
  checkout's own merge, so it needs the flag; an integrator in a worktree never does.

How the main checkout is told apart. Git is asked about the FILE's directory: the file's work tree
(`--show-toplevel`) is compared with the main worktree, the first entry of `git worktree list
--porcelain`. A path prefix cannot do it, because every worktree on this box sits inside the main
checkout's directory. Three more ways a path can still reach the main checkout's file are closed, each by
its own test:

| route | closed by |
|---|---|
| a hardlink to the main checkout's INSTRUMENTS.md | an identity comparison (`os.path.samefile`) with that file |
| a directory link, from a folder in no repository, to another file of the main checkout | the path is resolved before the `.git` walk-up and before git is asked |
| a hook's environment (`GIT_DIR` and its kin) naming another repository | git runs with the variables that redirect discovery removed |

If a `.git` sits above the file and git still cannot place it, the tool fails closed: refused unless
`--main-checkout`. A file with no `.git` anywhere above it is in no checkout, and is edited. Exit codes:
0 resolved; 1 not resolvable (as before: not exactly one hunk, or a block with no numbered heading);
2 refused. On 1 or 2 everything goes to stderr, the two naming lines included. `merge_wave.py` prints
`stdout or stderr`, so it shows the reason.

The resolution itself is unchanged in this step: the two blocks, ordered by their first numbered heading.
Reading is universal-newline and writing is LF, as before. A CRLF checkout, which `core.autocrlf=true`
makes on this box, is resolved, and git normalizes on add.

## 10. Lessons

- **A guard over git's document set sees a new file only after `git add`.** The slice's readers were run
  before the new record was staged. `tests/test_a_correction_is_findable_from_the_claim.py` reads the
  corpus with `git ls-files`, so the record's own correction pair was invisible to that run, and the first
  commit was red alone. It was caught after staging and amended before any push. Run corpus guards after
  staging, as `tests/test_no_committed_identity.py` is run after committing.
- **A crash in a subprocess reads as an assertion failure, so FAILED-only counting does not filter it.**
  13 of the 17 reds against the original tool were its FileNotFoundError, seen through a return-code
  assertion. They proved the tool depended on its location and nothing about any guard. Each guard got
  its own mutant. Read the failure text before counting a red.
- **A surviving mutant can be a fact about the harness's layout.** M6, the path left unresolved, survived
  while the test's link sat inside the worktree, because git resolves a junction itself when asked from
  inside a repository. Only a link from a folder in no repository makes the tool's own resolution the one
  defence, and that placement killed it. When a mutant survives, find the layout in which the guarded
  code is the only defence.
- **`git stash` is shared by every worktree of a repository** (`refs/stash` is one ref). To run a guard on
  a tree without this lane's uncommitted cites, the file was restored to HEAD and the cites re-applied by
  their script, not stashed. The re-application was byte-identical.
- **A tool must find its target from its invocation, never from where it is stored.** The resolver's
  hazard was one expression, `Path(__file__).parents[2]`, which was correct in exactly one folder.
